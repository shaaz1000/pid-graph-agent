Proceed with the evidence-reference design.

Also implement the stricter relationship/pairing validation, with one important constraint:

DO NOT turn it into another large LLM-generated claims system.

The purpose is to make grounding more precise while making the output protocol substantially smaller.

==================================================
1. APPROVED ARCHITECTURE
==================================================

Replace verbose LLM-generated claims as the PRIMARY grounding mechanism with compact evidence references.

The architecture should become:

Graph Tool
    |
    v
Structured Tool Result
    |
    v
Deterministic Evidence Registry
    |
    +----------------------+
    |                      |
    v                      v
LLM Answer           Grounding Facts
    |                      |
    v                      |
Evidence References        |
    |                      |
    +----------+-----------+
               |
               v
        Grounding Validator
               |
               v
           Final Answer

The graph/tool layer remains authoritative.

The LLM references evidence.

The validator resolves those references back to deterministic graph facts.

==================================================
2. EVIDENCE IDS
==================================================

Assign deterministic evidence identifiers to tool results.

For example:

Step 1:
find_entities("H1007")

R1 = complete result
E1.1 = H1007 / PlateHeatExchanger-1

Step 2:
traverse(...)

R2 = complete traversal result
E2.1 = first returned entity/path fact
E2.2 = second returned entity/path fact
...

Evidence IDs must be generated by application code.

The LLM must NEVER invent the IDs.

Evidence IDs should be stable within a single agent execution.

Do not require global persistence across questions.

==================================================
3. KEEP EVIDENCE STRUCTURED
==================================================

An evidence entry should retain enough information for deterministic validation.

Conceptually:

{
    "evidence_id": "E2.4",
    "kind": "traversal",
    "subject": {...},
    "predicate": "reachable_downstream",
    "object": {...},
    "path": [...],
    "properties": {...},
    "source_tool": "traverse",
    "step": 2
}

This is conceptual.

Use the project's existing typed models where possible.

Do not introduce unnecessary duplicate representations.

==================================================
4. COMPACT ANSWER CONTRACT
==================================================

The LLM should no longer need to generate verbose claims such as:

reachable(...)
identified_as(...)
is_a(...)

for every entity.

Instead produce something compact.

For example:

{
  "answer": "The downstream valves are V1, V2, V3...",
  "evidence_refs": ["R2"]
}

or, where individual attribution matters:

{
  "answer": "...",
  "evidence_refs": ["E2.1", "E2.4"]
}

Choose the smallest schema that preserves validation quality.

Do not make the model reproduce graph data that already exists in the evidence registry.

==================================================
5. APPROVE THE STRICTER RELATIONSHIP CHECK
==================================================

Implement the stricter validation you proposed.

However, think of this as:

RELATIONSHIP-AWARE GROUNDING

rather than merely a "same sentence" string rule.

Example:

Suppose evidence contains:

P4711
  |
 Pipe-A
  |
nominal_diameter = DN80

and separately:

P4712
  |
 Pipe-B
  |
nominal_diameter = DN50

The answer:

"P4712's line is DN80."

must FAIL grounding even though:

- P4712 exists in evidence
- DN80 exists in evidence

The validator must establish that the property/value is associated with the entity/relationship being asserted.

==================================================
6. KEEP RELATIONSHIP VALIDATION TARGETED
==================================================

Do not build a general-purpose natural-language theorem prover.

Focus on graph-specific factual assertions such as:

ENTITY + PROPERTY

P4711 has property X

EDGE/LINE + PROPERTY

line between A and B has nominal diameter X

ENTITY + RELATIONSHIP + ENTITY

A connects to B

ENTITY + DIRECTION + ENTITY

A is downstream of B

ENTITY + TYPE

V100 is a valve

ENTITY + PATH/FEEDS + ENTITY

P4711 feeds H1007

These are the facts most important for this assignment.

==================================================
7. SENTENCE-LEVEL SCOPE
==================================================

Sentence-level association can be used as a practical boundary.

For each sentence containing graph-specific factual information:

1. identify graph identifiers / tags / values in that sentence;
2. resolve the cited evidence refs;
3. verify that the referenced facts support their association, not merely their independent existence.

For example:

"P4711 feeds H1007 through line X, which has nominal diameter DN80."

requires evidence supporting the relevant relationships between:

P4711
H1007
line X
DN80

Do not accept four unrelated evidence facts merely because all four tokens occur somewhere.

==================================================
8. DO NOT OVER-ENGINEER NATURAL LANGUAGE PARSING
==================================================

If deterministic validation cannot confidently establish the relationship represented by a complicated sentence:

prefer:

validation uncertain
    ->
rewrite into simpler grounded sentences

rather than:

guess that it is supported.

This is especially useful because the model can produce atomic sentences such as:

"P4711 feeds H1007. [E3.2]"

"The connecting line has nominal diameter DN80. [E4.1]"

Atomic factual sentences are easier to validate than compound prose.

Encourage concise atomic engineering statements in the answer prompt.

==================================================
9. RESULT-LEVEL REFERENCES
==================================================

R-level references such as R2 are acceptable for enumeration.

Example:

"The downstream valves are V1, V2, V3, V4... [R2]"

The validator should expand R2 into the deterministic rows returned by the traversal.

Then verify that:

- every listed valve exists in R2;
- no additional unsupported valve was introduced;
- the relevant downstream relationship is represented by R2.

This is much better than requiring three claims per valve.

==================================================
10. PROPERTY CLAIMS SHOULD PREFER ROW-LEVEL REFERENCES
==================================================

For precise engineering properties, prefer narrow evidence.

Example:

"The nominal diameter is DN80. [E4.2]"

rather than referencing an enormous traversal result.

This makes incorrect pairing easier to detect.

The prompt may encourage:

broad result refs for enumeration
narrow evidence refs for precise properties/relationships

Do not make this brittle if the deterministic validator can resolve either safely.

==================================================
11. TRUNCATION HANDLING
==================================================

Implement finish_reason preservation.

At minimum distinguish:

stop
length
other/unknown

If:

finish_reason == "length"

do NOT run the response through normal answer parsing as though it were complete.

Represent it explicitly as truncated.

The workflow can then decide whether to:

- retry with a more compact prompt;
- request a concise rewrite;
- or safely withhold the answer.

Do not report "missing claims" when the actual failure is truncation.
